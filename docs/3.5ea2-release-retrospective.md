## What Went Well

1. **RC1 available 1 day after code freeze** — ldimaggi noted EA2 was in better shape than EA1, which took 22 working days from code freeze to GA
2. **Automated bot alerts** — rhoai-devops-bot and Alert app provided regular automated reports (upstream sync failures, blocker updates, Jira watcher)
3. **Same-day dashboard rebuild** — When CrashLoopBackOff was found on Jun 22, a fixed nightly was produced within hours
4. **Cross-team escalation worked** — Rakesh's manual escalation and team-tag pings eventually got blockers assigned
5. **Code freeze exception process** — Exception for RHAISTRAT-1276 was handled with clear approval and extended freeze date

## What Went Wrong

### Process Issues

1. **Jira API token expired on code freeze day** (Jun 16-19) — Blocker bot reported "0 blockers" while ~50 existed. Nobody noticed for ~3 days. The most critical moment (code freeze) had zero blocker visibility.

2. **Blocker report noise** — Alert bot mixed product blockers with TFA (Test Failure Analysis) test-failure blockers (both use `Priority=Blocker`). Demethria requested separate reports. khowell said: *"something is very wrong... there is so much text that the list of blockers is getting cut off"* and *"alerts are difficult to even read."*

3. **Alert fatigue** — sfroberg: *"many of us are getting continually pinged and interrupting our work. Personally I've been pinged at least a dozen times today on two of the same issues."*

4. **Post-code-freeze blocker surge** — 15 non-test blockers found within ~24h of RC1 (ldimaggi: "something is wrong here"). Many issues only discovered once real testing started.

5. **Stale blockers without owners** — RHOAIENG-69754 sat unassigned for 7+ days. RHOAIENG-63549 (Feast) had "6 days without update." Multiple blockers flagged as idle >2 working days before anyone responded.

6. **Fixes not backported to main** — Moulali flagged that fixes were landing on the release branch only. RHOAIENG-72341 was a regression that was fixed in EA1 but the dev team missed putting the fix in main, so it reappeared in EA2.

7. **SmartSheet deprecation** — Discovered mid-cycle that SmartSheet (a dependency) was decommissioned without notice, requiring migration to Product Pages API.

### Build/Architecture Issues

8. **s390x/ppc64le recurring failures** — odh-pipelines-components, odh-automl, odh-cli, odh-feature-server, vLLM-cpu, agent-ops-ui all failed on IBM Power/Z. Persistent cross-release theme from EA1.

9. **Go 1.26 upgrade broke multiple components** — model-registry, notebook-controller, mod-arch-gen-ai, cli all hit independently. No coordinated Go version upgrade.

10. **Upstream auto-merge failures without routing** — Multiple components tagged "unmapped" (llm-d-router, batch-gateway-operator, rhoai-mcp). No team received the alert.

11. **FIPS conflicts** — DSP pods CrashLoopBackOff from Go FIPS conflict (`GOLANG_FIPS` vs `GODEBUG=fips140`). check-payload doesn't support native Go FIPS (RHOAIENG-69742).

12. **Dashboard instability chain** — tslib missing → CrashLoopBackOff → agent-ops-ui not multi-arch → orphaned namespaces → page load timeouts.

13. **PCC cache stale on Jul 3** — FBC catalog PCC cache wasn't regenerated after RC2, requiring an additional FBC-only push to stage.

14. **Multiple push-to-stage retries** — RC2 push to stage took 3+ attempts due to process errors (~4 hours total).

### Conforma/EC Policy Issues

15. **Multi-arch RPM version mismatch** (RHAIENG-5321) — s390x builds picked up older openssl and python3 RPMs than other architectures because repos hadn't synced. Recurring blocker across many daily reports.

16. **DfFIPS violations emerged late** (Jun 28) — RHOAIENG-71907/71906 for Model-Registry and Serving-Runtime. Discovered after code freeze.

## Jira Deep-Dive: Patterns Found in Comments

### RHOAIENG-63549 — Feast operator upgrade (20 mentions, Blocker, Resolved)

**What happened:** Kubernetes `spec.selector` is immutable on Deployments. A fix for 3.3→3.4 (RHOAIENG-58369, "strip patch") introduced the same class of problem in reverse for 3.4→3.5. The initial fix attempt (a migration Job in the feast repo) failed because the ODH operator reconciliation loop applies Deployments before Jobs — the deploy fails before the migration Job is even created ("chicken-and-egg").

**Resolution timeline:** Reported May 20. Fix verified by QA on Jun 16. But the Jira wasn't closed until Jun 22 — 6 days with a verified fix sitting in "awaiting resolution" while the Slack channel kept flagging it as an open blocker. Someone also pointed out "migration from GA to EA1 is not supported" so it was deprioritized, then resurfaced for EA2.

**IC improvement — Regression detection:** This is the same bug class hitting twice (immutable selector labels). IC should detect when a component's Deployment `spec.selector` labels change between the previous GA and the current build. This is a known Kubernetes constraint — any label change will break upgrades.

**IC improvement — Verified-but-not-closed tracker:** QA verified the fix Jun 16 but the Jira stayed open until Jun 22. IC should flag blockers where the Jira status is still "open" but a comment says "verified" or "fixed" — stale blocker status inflates the blocker count unnecessarily.

### RHOAIENG-71268 — payload-processing CrashLoopBackOff (18 mentions, Blocker, In Progress)

**What happened:** OCP 4.22 introduced a default deny-all NetworkPolicy in `openshift-ingress`. A prior fix (PR #3682) only added egress rules for `kube-auth-proxy` but missed `payload-processing`. The AIPCC autofix bot created PR #3699, iterated 10 times through review comments, and the PR was eventually merged. But then a **secondary blocker** emerged: on ROSA clusters, a validating webhook blocks NetworkPolicy creation in `openshift-ingress` even from privileged service accounts.

**Resolution complexity:** Fix needed in 3 branches: `rhoai-3.5.EA2`, `rhoai-3.4.x`, and `main`. Demethria had to ask "which release is this actually being included in?" because Fix Version was unclear.

**IC improvement — OCP version compatibility matrix:** When a new OCP version (4.22) introduces breaking changes (NetworkPolicy defaults), IC should flag ALL components deploying pods into affected namespaces, not just the one that was reported. The `kube-auth-proxy` fix existed but `payload-processing` was missed — a systematic scan would catch all pods.

**IC improvement — Multi-branch fix tracking:** Scott Froberg said "This needs to be fixed in RHOAI 3.5-ea2, 3.4.x and main." IC should track whether a blocker fix has landed in all required branches, not just the current release branch. This directly relates to the backport tracking improvement.

### RHOAIENG-69754 — Deploy model wizard storage bug (16 mentions, Blocker, Backlog — unassigned)

**What happened:** The `applyConnectionData()` webhook sets connection annotations but doesn't populate `spec.predictor.model.storage`. The autofix bot created a PR in the dashboard repo, but then the issue was reassigned from Dashboard to Platform team ("this is not a dashboard code issue"). The transient webhook failure couldn't be reproduced on clean clusters — only on the specific EA2 cluster used for the Fraud Detection tutorial. Rejected as blocker for EA2, moved to 3.5 GA.

**Resolution pattern:** Issue bounced between 3 teams (Dashboard → Zaffre/Model Serving → Platform) over 12 days. Each reassignment reset context. The autofix bot's PR was against the wrong repo (dashboard) since the root cause was in the connections API webhook.

**IC improvement — Issue bounce detection:** IC should detect when a Jira issue is reassigned to a different component/team more than twice without resolution. This "hot potato" pattern always delays fixes.

**IC improvement — Tutorial/demo validation:** The Fraud Detection tutorial is customer-facing and caught this bug. IC could run automated validation of official tutorials against each RC build before flagging readiness.

### RHAIENG-5321 — Conforma RPM mismatch (14 mentions, Blocker, Resolved)

**What happened:** s390x builds had older `openssl` and `python3` RPM versions than other architectures. Jiri Danek's analysis (Jun 2) revealed a critical insight: **the lockfile consistency test would NOT have caught this** because the mismatch comes from the UBI9 base image, not from the lockfile-installed RPMs. The base image on s390x hadn't been rebuilt with the latest RPMs at build time. Additionally, s390x installs `python3-devel` which upgrades system `python3` to the lockfile version, while other arches don't install it — creating a *forward* version divergence.

**Fix was delayed by sync lag:** Vath Sok's fix merged to `main` on Jun 9, but the upstream-to-downstream sync to `rhoai-3.5-ea.2` was days behind. He had to manually ask Moulali to re-sync.

**IC improvement — Base image RPM drift detection:** Jiri Danek proposed SBOM-based cross-arch comparison (`cosign download sbom` per architecture). IC should implement this: compare `pkg:rpm/` entries in SBOMs across architectures for multi-arch images. Only 4 base images to check, ~2s each. This is the only way to catch base-image-level divergence before Conforma flags it post-build.

**IC improvement — Upstream-to-downstream sync delay alerting:** When a blocker fix merges to `main` but doesn't appear in the release branch within 24h, IC should alert. The sync lag was 2+ days in this case.

### RHOAIENG-70907 — vLLM images (18 mentions, Blocker, In Progress)

**What happened:** RHOAI consumes vLLM images from a separate product (RHAII = Red Hat AI Infrastructure). The images were available on `registry.stage.redhat.io` but not `registry.redhat.io` (production), which is expected during EA. However, the build configuration was trying to pull from the prod registry, causing `manifest unknown` errors. Additionally, Gaudi hardware validation is still blocked as of Jul 6 because Intel hardware is unavailable.

**IC improvement — Cross-product image dependency tracking:** When RHOAI depends on images from RHAII (or other products), IC should verify the images exist in the expected registry (stage vs prod depending on release phase). The `registry.redhat.io` vs `registry.stage.redhat.io` mapping was missing in the build config — IC could detect this by checking if referenced images resolve.

**IC improvement — Hardware dependency tracking:** Gaudi/Spyre validation requires specific hardware that may not be available. IC can't fix hardware availability, but it CAN flag "validation blocked >N days due to hardware" so release managers know this is a long-pole item.

### RHOAIENG-68504 — OGX Vertex AI event loop crash (14 mentions, Blocker, Resolved)

**What happened:** The `VertexAIInferenceAdapter` creates its `google-genai` client in a temporary event loop during init. When inference requests arrive on the uvicorn serving loop, the httpx client is still bound to the dead init loop, causing `RuntimeError: Event loop is closed`. This affects both `google-genai` 1.x and 2.x. GCP secrets were removed from the repo as a workaround (disabling Vertex/Gemini CI tests).

**IC improvement — CI test coverage tracking:** IC should flag when CI tests are being skipped/disabled as a workaround for a bug rather than a deliberate policy choice. The removal of GCP secrets disabled all Vertex AI smoke/integration tests — IC should surface this as a "test coverage regression" alert.

## What IC Could Improve / Anticipate

### High Priority — Would have caught problems earlier

1. **Monitor Jira API token health** — IC should check that the Jira API token is valid and alert if it's expired or about to expire. The 3-day blindspot during code freeze was the most impactful failure of the release.

2. **Separate blocker categories** — IC alerts should distinguish between product blockers and test-failure blockers. Right now both show as "Blocker" priority and overwhelm the signal. Add a filter/grouping by blocker source (product bug vs TFA test failure).

3. **Track blocker age and assignment** — IC should flag: (a) blockers unassigned >24h, (b) blockers without updates >48h, (c) blockers that recur across releases (like s390x builds), (d) blockers verified-but-not-closed (RHOAIENG-63549 sat 6 days as "open" after QA verified the fix). These patterns were manually escalated by Rakesh but should be automatic.

4. **Detect upstream auto-merge "unmapped" components** — When the upstream-to-downstream bot reports a failure for a component with no team routing, IC should flag it specifically so someone adds the mapping.

5. **Go toolchain upgrade tracker** — When a Go version change appears in one component, IC should check all other Go-based components for compatibility. The Go 1.26 upgrade broke 4+ components independently.

6. **PCC cache staleness after releases** — IC already tracks PCC staleness but the Jul 3 incident shows it needs to run after every push-to-stage, not just nightly. Add a post-push check.

7. **Base image RPM drift detection (SBOM-based)** — Compare RPM package versions across architectures in multi-arch images using SBOM data (`cosign download sbom`). RHAIENG-5321 showed this is the only way to catch base-image-level divergence — the lockfile test can't detect it. Jiri Danek proposed this approach and it's lightweight (~2s per image).

8. **Multi-branch fix propagation tracker** — When a blocker fix merges, track whether it's landed in all required branches (main, release branch, z-stream). RHOAIENG-71268 needed fixes in 3 branches and Demethria had to manually chase which release it was targeting. RHAIENG-5321's fix was delayed 2+ days because the sync from main to rhoai-3.5-ea.2 was behind.

9. **Issue bounce detector** — Flag Jira issues reassigned to a different component/team more than twice without resolution. RHOAIENG-69754 bounced between Dashboard → Zaffre → Platform over 12 days, resetting context each time.

10. **OCP version compatibility scanner** — When a new OCP version introduces breaking changes (like OCP 4.22's deny-all NetworkPolicy), IC should scan ALL components deploying pods into affected namespaces. RHOAIENG-71268 was missed because the prior fix (PR #3682) only covered `kube-auth-proxy` but not `payload-processing`.

### Medium Priority — Would reduce noise and improve process

11. **Alert deduplication** — Multiple people complained about being pinged 12+ times for the same issue. IC alerts should deduplicate: don't re-alert on the same component/Jira if status hasn't changed.

12. **Multi-arch build readiness** — Before code freeze, IC should report which components have NOT been built successfully for all target architectures (s390x, ppc64le, arm64, x86_64). This was a recurring surprise.

13. **FBC fragment SHA tracking** — During RC testing, multiple FBC fragment SHAs were produced in a single day (3 on Jun 22). IC should track which SHA is "current" and which test runs map to which SHA.

14. **Cross-product image dependency tracking** — When RHOAI depends on images from RHAII or other products, IC should verify images exist in the expected registry (stage vs prod). RHOAIENG-70907 failed because `registry.redhat.io` mapping was missing — the image was only on `registry.stage.redhat.io` as expected during EA, but the build config referenced the prod registry.

15. **CI test coverage regression detection** — Flag when CI tests are disabled as a workaround rather than a deliberate policy choice. RHOAIENG-68504 led to removing GCP secrets, disabling all Vertex AI smoke/integration tests. IC should surface this as a "tests silently skipped" alert.

16. **Deployment selector label freeze enforcement** — Kubernetes `spec.selector` is immutable on Deployments. When a component changes its Deployment selector labels between releases, it will break all upgrades. IC should detect this by comparing manifests between the previous GA and the current build (RHOAIENG-63549 hit this pattern twice: 3.3→3.4 and 3.4→3.5).

### Lower Priority — Nice to have

17. **Code freeze countdown** — IC should show days-to-code-freeze and highlight components with open build failures or conforma violations that aren't in progress.

18. **Exception lifecycle tracking** — Track which Conforma exceptions have been created, whether they're still needed, and whether the root-cause fix has landed.

19. **Release readiness dashboard** — A pre-RC checklist that aggregates: (a) all arches built, (b) conforma clean or excepted, (c) upstream syncs passing, (d) no stale nightly builds, (e) snapshot complete. Much of this exists in `ic release readiness` but needs the new checks from the plan.

20. **Post-push-to-stage validation** — After a push to stage, automatically verify the release CR status (`Released=True`, no `failedPostValidation`), FBCF images published for target OCP versions, and test clusters are receiving the correct images.

21. **Hardware dependency tracking** — Flag when validation is blocked >N days due to hardware unavailability (e.g., Gaudi/Spyre). IC can't fix hardware, but release managers need visibility on long-pole items.

22. **Tutorial/demo validation** — Run automated validation of official tutorials (e.g., Fraud Detection) against each RC build. RHOAIENG-69754 was only caught because someone manually ran the tutorial.

## Glossary

- **EA**: Early Access — pre-GA milestone release
- **RC**: Release Candidate — build considered for stage/prod push
- **GA**: General Availability — final public release
- **FBC**: File-Based Catalog — OLM operator catalog fragment
- **FBCF**: FBC Fragment — component of the OLM catalog for a specific OCP version
- **PCC**: Pre-Computed Catalog — cached version of the operator catalog for faster install
- **TFA**: Test Failure Analysis — automated test result categorization
- **EC**: Enterprise Contract — policy evaluation system (Conforma)
- **RPA**: ReleasePlanAdmission — Konflux CR that defines release gate configuration
- **MaaS**: Model as a Service — RHOAI model serving feature
- **OGX**: OpenAI Gateway Proxy (formerly LiteLLM proxy)
- **DSP**: Data Science Pipelines
- **FIPS**: Federal Information Processing Standards — cryptographic compliance requirement
- **DfFIPS**: Docker/container FIPS check (check-payload verification)
- **RHAII**: Red Hat AI Infrastructure — separate product providing vLLM images
- **RHCL**: Red Hat Cluster Lifecycle operator
- **CRD**: Custom Resource Definition — Kubernetes API extension
- **s390x**: IBM System Z architecture
- **ppc64le**: IBM Power architecture (little-endian)
